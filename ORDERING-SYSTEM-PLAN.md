## Context

The restaurant owner wants pikMe customers to be able to order ahead for pickup and pay in-app, rather than only browsing menus. This is a genuinely new feature area — nothing in the current codebase does this. Three product decisions shape the whole design, confirmed directly with the user before this plan was drafted:

- **Pickup only** — no delivery logistics.
- **Pay in-app, 100% to the restaurant.** A real payment processor (not Apple IAP — Apple requires real processors for physical goods, so this is compliant), with pikMe taking **zero** per-order cut. pikMe's revenue for this feature is a **flat monthly fee charged to the restaurant**, tracked separately from the payment flow (an admin-toggled flag for v1, not a self-serve subscription system).
- **Claimed restaurants only**, and the restaurant-facing order screen is explicitly **"a website that refreshes its screen"** — a kiosk display meant to sit on a tablet/monitor in the restaurant, not a mobile-app flow.
- **Sales tax skipped for v1** (order total = sum of item prices, with an in-app note that tax/fees may be collected at pickup). **No push notifications required for v1** — the kiosk is solved by polling, and the customer can poll an order-status screen while in the app.

Three research passes (payments, pricing/owner-app structure/push, coupon lifecycle/owner-auth patterns) confirmed this is genuinely greenfield: **no pricing data exists anywhere** (`menu_items` has zero price columns), **no payment infrastructure exists anywhere** (the `coupons` system never moves real money — it's a "show a discount code to staff" flow per its own migration comment), and **no push notifications or Supabase Realtime usage exist anywhere in the repo** (all "live" data today is plain polling/manual refresh).

## Key architectural decisions

- **Pricing lives in a new overlay table (`menu_item_prices`), not on `menu_items` itself.** `menu_items` rows are often a shared, name-keyed template across multiple claimed locations of the same chain (migration `067_menu_items_place_id.sql` added a nullable `place_id` for a location to fork its own row, but that fork — stage 2 of an already-separate, on-hold per-location-menus project — hasn't shipped). Putting price directly on `menu_items` would be meaningless on shared template rows, since the same dish can legitimately cost different amounts at different locations. A `(restaurant_id, item_id)`-keyed overlay table sidesteps this entirely and has zero dependency on that other project's stage 2 — **but should still be sanity-checked against that project before Phase 1 starts**, since it's the single biggest schema call in this plan.
- **Stripe Connect, Express accounts, destination charges, zero application fee** — restaurant gets 100%, pikMe's platform account never holds the money. Express (not Standard) because pikMe's only involvement is a one-time KYC handoff; day-to-day Stripe stays the restaurant's own relationship.
- **The restaurant kiosk is a new route inside the existing `owner` Expo app's web build**, not a standalone app — `owner/` is already `expo start --web`-exportable and already has owner auth, the `restaurants.owner_id` ownership checks, and Supabase client wiring. A standalone app would duplicate all of that for no benefit.
- **Polling, not Realtime**, everywhere — matches the repo's existing all-polling pattern (confirmed zero `.channel(`/`postgres_changes` usage anywhere today).
- **Payment confirmation is webhook-verified, never client-trusted.** The client's PaymentSheet success callback is a UX hint only; a Stripe webhook with signature verification is the only thing allowed to flip an order from `pending_payment` to `placed`.

## Database schema

All migrations are new, numbered sequentially from the current max (158). Each ships with a matching `supabase/tests/<n>_<name>.test.sql` (rolled-back transaction, `RAISE NOTICE 'ALL <n> TESTS PASSED'`) and a README row, per existing convention.

**`160_restaurant_ordering_settings.sql`** — one row per restaurant: `ordering_enabled` (the flat-monthly-fee master switch, admin-only), `enabled_at`/`enabled_by`, `billing_notes` (free text — fee/cadence, manually tracked), `pickup_instructions`, `average_prep_minutes`, and **`kiosk_token TEXT UNIQUE NOT NULL DEFAULT gen_random_uuid()::TEXT`** plus **`kiosk_token_expires_at TIMESTAMPTZ NOT NULL`** — set automatically the moment `admin_set_restaurant_ordering_enabled` turns ordering on for a restaurant, so a working kiosk link exists from day one with no setup step for the owner. **The link expires** — by default at midnight that night in the restaurant's own local time, **not UTC** (UTC midnight would land mid-service for most US timezones) — but the owner can pick a different expiry when generating or regenerating it (e.g. a week, for a restaurant that doesn't want to redo this daily). Past expiry, the link simply stops working until a new one is issued — this is a deliberate security boundary, not an oversight. Since the link itself is the only credential (no login), it's inherently shareable by design — the real risk isn't an outside attacker guessing a UUID, it's **staff forwarding the working link to someone else** (a friend, a former coworker, anyone), who could then view and act on live orders indefinitely if the link never expired. Daily expiry bounds that exposure to one business day by default, without requiring the owner to track or revoke anything manually.

**Operational consequence worth flagging now**: with the midnight-default, an owner who doesn't override it needs to regenerate and re-share the link every morning before opening. This makes the QR-code idea (discussed earlier, originally a nice-to-have) worth pulling into Phase 1 rather than deferring — daily copy/paste/email is real friction, daily QR-scan is not. See "Restaurant kiosk screen" below. Structural cousin of `139_listing_eligibility.sql`'s per-restaurant gate table. RPCs: `admin_set_restaurant_ordering_enabled` (admin-only, `_require_admin()`), `admin_get_restaurant_ordering_settings`, `owner_update_ordering_display_settings` (owner can edit display fields, not the enabled flag), `owner_get_kiosk_link` (owner-auth, pure read — returns the restaurant's existing token/link/expiry, no side effects, safe to call every time the owner opens the Kiosk Access screen), `owner_regenerate_kiosk_token(p_restaurant_id, p_expires_at DEFAULT NULL)` (owner-auth, the *only* mutation — explicit action; when `p_expires_at` is omitted, defaults server-side to midnight tonight in the restaurant's local time; the owner can instead pass a custom timestamp. Returns the new token, link, and expiry, and immediately invalidates the old token).

**`161_menu_item_prices.sql`** — `(restaurant_id, item_id)` primary key, `price_cents CHECK (> 0)`, `currency`, `is_active`. RPCs: `owner_set_menu_item_price`, `owner_list_menu_item_prices`, and the public read `get_orderable_menu_items_for_restaurant(p_restaurant_id)` — resolves the restaurant's visible item set the same way `get_menu_items_for_restaurant` already does, inner-joins active prices, and additionally requires `ordering_enabled = true` + `restaurant_owners.is_active = true` + restaurant approved + not paused (an owner who stops paying the flat fee gets deactivated via the existing admin tool — see Open Decision 5 — and this is the check that actually turns their ordering off as a result).

**`162_restaurant_payment_accounts.sql`** — `restaurant_id` PK, `stripe_account_id`, `charges_enabled`/`payouts_enabled`/`details_submitted`. Owner can `SELECT` their own row; all writes are service-role only (edge functions), same shape as `006`/`007`/`010`.

**`163_orders.sql`** — `orders` (status enum: `pending_payment → placed → accepted → ready → completed`, plus `rejected`/`canceled`/`payment_failed`; `stripe_payment_intent_id` unique; `refund_status`; `client_idempotency_key TEXT UNIQUE` — a UUID the `user` app generates once per checkout attempt and re-sends on any retry, so a double-tap or a flaky network retry can't create two orders for the same cart (`create-order-payment-intent` checks for an existing order with that key first and returns it instead of creating a duplicate; the same key is also passed as Stripe's own `Idempotency-Key` header on the PaymentIntent call); timestamps per transition) and `order_items` (snapshotted `name_snapshot`/`unit_price_cents` at order time — never re-read live price, same reasoning as why menu items get snapshotted rather than FK'd loosely elsewhere in this codebase). **No direct INSERT/UPDATE/DELETE grants** on either table — every write goes through `SECURITY DEFINER` RPCs, same reasoning already documented on `coupon_activations`.

Three separate families of write RPCs, reflecting three separate identities that can touch an order:
- **Owner-authenticated** (`owner_accept_order`, `owner_mark_order_ready`, `owner_mark_order_completed`, `owner_reject_order`) — for the owner's own logged-in view of their orders (e.g. from `dashboard.tsx`), using the exact inline owner-auth check already used everywhere else in this codebase (`052_restaurant_pause_toggle.sql`, `009_coupon_functions.sql`).
- **Kiosk-token-authenticated** (`kiosk_get_orders(p_kiosk_token)`, `kiosk_accept_order(p_kiosk_token, p_order_id)`, `kiosk_mark_order_ready(...)`, `kiosk_mark_order_completed(...)`, `kiosk_reject_order(...)`) — for the unauthenticated kiosk screen (see below). **This is where rejection will happen in practice day to day**, since the kiosk — not the owner logging into their own app — is where staff actually work. Each validates `p_kiosk_token` against `restaurant_ordering_settings.kiosk_token` **and** `kiosk_token_expires_at > NOW()` to resolve the restaurant, instead of `auth.uid()` — an expired-but-otherwise-correct token is refused the same as a wrong one. `SECURITY DEFINER`, `GRANT EXECUTE ... TO anon` — the same shape as this codebase's existing anon-granted, identifier-scoped public functions (e.g. `get_place_share_info`, `restaurant_is_listed`), just scoped by an opaque, time-bounded token instead of a place id.
- **Customer-authenticated** (`customer_cancel_order(p_order_id)`) — lets the customer back out of their own order (wrong restaurant, ordered by mistake, changed their mind), checked via `customer_id = auth.uid()`. Only allowed `WHERE status = 'placed'` — once the restaurant has accepted and started prepping, cancellation is no longer available to the customer (a reject from the restaurant side is still possible).

Both families share the identical atomic-claim idiom from `activate_coupon` (`UPDATE ... WHERE id = ... AND status = '<expected>' RETURNING id`) so two taps — from the owner app and the kiosk, or two kiosk taps — can't double-fire.

## Payment architecture

- **Onboarding — each restaurant gets its own separate connected account.** pikMe holds exactly one Stripe platform account; every restaurant's own bank details go **directly into Stripe's own hosted onboarding form**, never through pikMe's servers at all. Owner taps "Connect bank account" on a new `owner/app/restaurant/payments.tsx` → `restaurant-connect-onboarding` edge function creates/reuses that restaurant's Express account + an Account Link (a one-time Stripe-hosted URL) → owner completes Stripe-hosted KYC/bank-account entry there → `restaurant-connect-refresh-status` pulls current status immediately on return (don't wait on the webhook for the UI). From then on, pikMe only ever references the restaurant by its `stripe_account_id` (`restaurant_payment_accounts.stripe_account_id`) — Stripe is what's actually integrated with the banking network, not pikMe.
- **Checkout**: `create-order-payment-intent` (customer-authenticated) **re-prices every line item from `menu_item_prices` server-side** (never trusts a client-sent price), **refuses the order if the subtotal is below `app_config.orderingMinimumCents`** (default $3.00, admin-editable) **or if any line item's quantity exceeds `app_config.orderingMaxItemQuantity`** (a sanity cap against a fat-fingered or abusive order — default 20, admin-editable, same generic Config Management pattern), inserts `orders`/`order_items` as `pending_payment`, creates the PaymentIntent with `transfer_data.destination` set to the restaurant's account and no application fee, returns `client_secret`. Client uses `@stripe/stripe-react-native`'s PaymentSheet (keeps pikMe out of PCI scope — SAQ-A).
- **Confirmation**: `stripe-order-webhook` (Stripe-signature verified, no user auth) is the only path that flips `pending_payment → placed`/`payment_failed`/`canceled`. `stripe-connect-webhook` keeps `restaurant_payment_accounts` in sync on `account.updated`.
- New edge functions: `restaurant-connect-onboarding`, `restaurant-connect-refresh-status`, `stripe-connect-webhook`, `create-order-payment-intent`, `stripe-order-webhook`, and (Phase 2) **`kiosk-reject-order`** + **`owner-reject-order`** — both call their respective `*_reject_order` RPC and then **immediately issue the full Stripe refund in the same call**, no separate confirm step. The kiosk one is the one that matters most in practice.
- Secrets as Edge Function secrets, never `app_config` (that table explicitly excludes real secrets): `STRIPE_SECRET_KEY`, `STRIPE_CONNECT_WEBHOOK_SECRET`, `STRIPE_ORDER_WEBHOOK_SECRET`. `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` in the `user` app's env (safe to expose).

## Restaurant kiosk screen

**Access model: a secret link, not a login.** Staff need to see and run the order queue without being able to reach anything else on the owner side (payouts, Stripe settings, coupons, menu editing) — confirmed explicitly with the product owner. So the kiosk is **not** gated by the owner's real Supabase Auth session at all:

- New top-level route `owner/app/kiosk/[token].tsx`, living entirely **outside** the `owner/app/restaurant/` tree (not just outside its header chrome) — it has zero dependency on `restaurantOwnerStore` or any owner-auth guard, so it's structurally incapable of reaching any other owner screen even by hand-editing the URL, since every other route still requires a real logged-in owner session.
- It calls the `kiosk_*` RPCs (above) with the token straight from the URL — no sign-in step, nothing else to type. Staff just open the bookmarked link on the tablet/monitor and leave it open.
- The owner gets a **"Kiosk Access"** section (on `payments.tsx` or its own small screen) showing the current kiosk link **and its expiry**, with Copy, **a QR code** (brought into Phase 1 rather than deferred — see below), and Regenerate. Regenerating defaults to "expires tonight at midnight," with an option to pick a longer custom expiry — the owner's daily routine (or one-time setup, if they choose a long custom expiry instead) for getting a fresh link onto the tablet.
- **Why the QR code matters now, not later**: with the midnight-default expiry, an owner who doesn't override it needs a fresh link on the tablet every morning. Scanning a QR code shown on the owner's own phone/laptop is a few-second daily habit; copy/paste/email is real friction repeated every day. The QR code is just a rendering of the same URL — no new backend, cheap to build alongside the link/Copy button.
- The kiosk screen itself checks its own token's expiry client-side too (it already has the expiry from the last successful `kiosk_get_orders` response) and shows a plain "This link has expired — ask the restaurant for today's new one" message once it lapses, rather than just silently failing polls.
- **Recommended setup flow, shown as in-app guidance on the Kiosk Access screen** (not something the app can force, but worth designing the UX around): the owner opens the kiosk link on the tablet itself and uses the browser's **"Add to Home Screen"**, which launches it full-screen with no address bar at all — a plain `window.open()` popup can't reliably hide the URL bar on modern mobile browsers (iOS Safari in particular blocks this, for good reason — it used to be a phishing trick), so "Add to Home Screen" is the real mechanism that achieves "staff never sees or can copy the raw URL," not a popup trick. Right after the owner opens the kiosk link from their own logged-in session, show a one-time prompt — **"Kiosk is set up on this device. Sign out of your owner account now?"** — since the kiosk never needed that owner session to begin with (it only ever authenticates via the token); this closes the gap where an active owner session could otherwise be reached from the same tablet via its regular browser.
- Same polling behavior as before: `kiosk_get_orders` every ~8-10s (pausing when the tab isn't visible, manual refresh, "last updated Xs ago"), active orders (`placed`/`accepted`/`ready`) oldest-first, large Accept/Reject/Ready/Completed tap targets.
- Token strength: `gen_random_uuid()`-based (122 bits of entropy) — effectively unguessable, so an anon-granted, token-scoped function is safe without additional rate-limiting, consistent with how this codebase already treats UUIDs/place IDs as sufficiently opaque elsewhere.

Carried-forward limitation worth knowing, not something this feature introduces: `owner/src/store/restaurantOwnerStore.ts` models one restaurant, not a list, even though one owner account can legitimately own multiple restaurants (no uniqueness constraint on `restaurants.owner_id`, confirmed via migration `071`'s own comment) — a multi-location owner gets one kiosk link per location, which is actually a natural fit here (each location's tablet gets its own link anyway).

## Phase breakdown

**Phase 0 — Prerequisites**: sign off on the `menu_item_prices` design against the on-hold per-location-menus project; resolve the open decisions below (several reshape the state machine, can't be half-built); create pikMe's Stripe platform account + Connect (Express), provision secrets. **Confirm whether `restaurants` already stores a timezone** (used today for displaying posted hours like "Opens tomorrow"/"Closes in 17m") — the midnight-expiry default assumes this exists and is reused, not reinvented; if it doesn't exist, adding a `restaurants.timezone` column is itself a small prerequisite migration, since the server can't compute "local midnight" without knowing what timezone a restaurant is actually in.

**Phase 1 — MVP** (minimum for one real restaurant to take one real paid pickup order): migrations 160-163 + tests; the 5 core edge functions; owner `payments.tsx` + `menu-pricing.tsx` (parallel to existing `menu-nutrition.tsx`) + the Kiosk Access link screen + the token-gated `owner/app/kiosk/[token].tsx` route; user app cart/checkout/status screens; admin `ordering.tsx` toggle. Explicitly deferred: reject/refund/cancel flow, push notifications, order history.

**Go-live approach**: the first real restaurant is a **hands-on, admin-assisted pilot**, not a self-serve rollout — admin walks that one restaurant through Stripe Connect onboarding and pricing setup directly, Phase 1 runs end-to-end against real orders for a while before `ordering_enabled` is offered more broadly. Given real money is involved from day one, this isn't assumed to just work at scale on the first try.

**Phase 2 — Operational hardening**: `kiosk-reject-order` + `owner-reject-order` + `customer-cancel-order` edge functions, all sharing the same immediate-refund logic (reject and customer cancellation both need real Stripe refunds, so this is built once for all three); admin alerting for stuck orders/failed refunds; a manual "re-sync this order from Stripe" admin safety-net action; basic abuse guard (cap pending orders per customer per restaurant); **a lightweight scheduled sweep that cancels any `pending_payment` order older than 30 minutes** (customer abandoned checkout mid-payment) — reusing the same cron-style scheduled-job pattern already used elsewhere in this codebase (e.g. the menu-build job), not a new kind of infrastructure; no-show handling per whatever policy is decided.

**Phase 3 — Nice-to-haves**: real push notifications (a cheap chime + visual flash on the kiosk for new orders is a low-cost partial substitute worth pulling earlier); customer order history; scheduled/future pickup times (v1 is ASAP-only); self-serve subscription billing if volume ever justifies it; receipts/email confirmations.

## Open business decisions — not assumed, need your call before Phase 1 locks in

1. ~~**Accept/Reject vs. always-accept**~~ — **Resolved**: kept. A restaurant can reject a paid order (out of an item, too busy, closing early, etc.), most often from the kiosk.
2. ~~**Refund mechanics on rejection**~~ — **Resolved**: automatic and immediate — the instant staff rejects, the full refund fires in the same call, no separate confirm step. Any Stripe refund-fee asymmetry lands on the restaurant's own connected account, since pikMe takes 0%.
3. ~~**No-show handling**~~ — **Resolved**: the restaurant keeps the payment, no automatic refund path. Still worth a small Phase 2 decision (not blocking): whether a `ready` order should auto-flip to `completed` after some timeout purely for reporting cleanliness, or just stay `ready` until staff taps it.
4. ~~**Minimum order amount**~~ — **Resolved**: `app_config` key `orderingMinimumCents`, global default `300` ($3.00), admin-editable via the existing generic Config Management page (same pattern as `cityCrawlMaxCalls`). `create-order-payment-intent` refuses checkout below it with a clear message, before creating any PaymentIntent.
5. ~~**Flat monthly fee mechanics / billing lapse**~~ — **Resolved, and simpler than originally proposed**: no separate lapse-handling mechanism needed. `restaurant_owners.is_active` already exists in this codebase and already blocks sign-in entirely (`restaurant-auth-login` already rejects a deactivated owner, confirmed in migration `058`). When a restaurant stops paying, admin deactivates the owner account via that existing tool — `get_orderable_menu_items_for_restaurant` and the order-placement path should additionally check `restaurant_owners.is_active = true` (alongside `ordering_enabled`), which they were always going to touch via the owner join anyway.
6. ~~**Kiosk login/security model**~~ — **Resolved**: staff access the kiosk via a secret, regenerate-able link scoped only to that one restaurant's orders, with zero access to the rest of the owner site. See "Restaurant kiosk screen" above.
7. ~~**App Store sequencing**~~ — **Resolved**: ship this well after the current Apple review lands, not bundled into the same cycle.
8. **Stripe Connect liability specifics** — merchant-of-record status, chargeback/dispute liability, and what happens if a restaurant's Express onboarding never reaches `charges_enabled` are legal/business questions, not engineering ones. The likely real answer is a new **owner-facing "Ordering Terms" agreement restaurants accept before enabling ordering** — covering exactly these points — drafted by actual counsel, not assumed or written here. **This is a launch gate, not a build gate**: all of Phase 0/1 can be built and fully tested in Stripe test mode without it — it only has to be resolved before `ordering_enabled` is ever turned on for a real restaurant with real money flowing, so it can run in parallel with engineering rather than blocking the start of work.
9. ~~**Customer-facing ordering disclaimer**~~ — **Resolved**: a **separate, new agreement** from the existing food/nutrition disclaimer (that one is scoped to nutrition-estimate accuracy; this one is about the transaction itself) and separate from #8's owner-facing Stripe terms (different party, different content). Reuses the existing versioned-agreement infrastructure (`005_user_agreements_table.sql`, the same pattern as the nutrition-disclaimer agreement in migration `024`) as a new agreement type, accepted once before a customer's first order — covers: the restaurant, not pikMe, prepares and is responsible for the order; a no-show forfeits the payment; tax/fees may be collected at pickup; the refund policy in plain terms. Exact wording is still for counsel to draft, same as #8, but the mechanism (reuse existing agreement infra, gate it at checkout) is settled.
